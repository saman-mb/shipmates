# Shipmates

A crew of specialist AI agents and command workflows that drive a GitHub issue from open to a reviewed, CI-green pull request — autonomously. Runs on Claude Code today; builds for eight more harnesses. Claude Code is fully runtime-verified; antigravity, cursor, pi and opencode have captain-attested live runs recorded in `tools/harness_matrix.json`.

## What it is

Shipmates is an open-source (MIT) crew of specialist AI agents: **13 domain-neutral subagents** and **18 command workflows**. It runs on [Claude Code](https://claude.com/product/claude-code) today, and installs for eight more harnesses — opencode, Antigravity CLI, Codex CLI, Cursor, GitHub Copilot, Pi, Grok Build, and Windsurf — see [Scope & honesty](#scope--honesty) for what each has and has not been verified against. Its flagship, `/shipmates-ship-issue`, takes a GitHub issue all the way to a reviewed, CI-green pull request on its own — it plans the work, builds it in an isolated git worktree, waits for CI to go green, convenes an adversarial review board, loops on the fixes within bounds, and hands you a PR to merge.

## Who it's for

Developers who want to hand off whole *tickets* — not just single prompts — to a crew of specialist agents. The agents are domain-neutral: they hold the work to the standard in **your** repo's `README` / `AGENTS.md` (or `CLAUDE.md` on Claude Code), so the same crew works on a game engine, a web app, or a CLI, in any language.

## The crew (13)

`architect` · `senior-engineer` · `principal-engineer` · `sdet` · `security-engineer` · `site-reliability-engineer` · `performance-engineer` · `devops-engineer` · `product-manager` · `ux-ui-designer` · `art-director` · `technical-writer` · `data-scientist` — each defined in `crew/<role>.md`.

## The commands (18)

`/shipmates-ship-issue` · `/shipmates-ship-epic` · `/shipmates-fix-bug` · `/shipmates-report-bug` · `/shipmates-plan-epics` · `/shipmates-consolidate-issues` · `/shipmates-harden` · `/shipmates-spike` · `/shipmates-migrate` · `/shipmates-document` · `/shipmates-release` · `/shipmates-polish` · `/shipmates-pr-review` · `/shipmates-qa` · `/shipmates-onboard` · `/shipmates-refactor` · `/shipmates-deslop` · `/shipmates-upgrade` — each defined in `commands/<name>.md`.

## Install

`shipmates` is a single Rust binary. Grab it any way you like:

**macOS / Linux (Homebrew):**
```bash
brew install saman-mb/tap/shipmates
```

**Anywhere (Cargo):**
```bash
cargo install shipmates
```

**Binary Installer (cargo-dist):**
```bash
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/saman-mb/shipmates/releases/download/vX.Y.Z/shipmates-installer.sh | sh
```

Then `shipmates install --harness <name>` drops the harness's own tree (`.claude/`, `.opencode/`,
`.codex/`, …) into the current directory — or `--dir` for a specific project. `shipmates targets`
lists every harness.

## Working in this repository

If you are an AI agent (or a human) contributing to Shipmates itself:

- **The one hard rule: keep agent roles domain-neutral.** No role may name-drop a stack, framework, or product — each enforces whatever *the user's* `README` / `AGENTS.md` (or `CLAUDE.md`) says. That neutrality is what lets the crew sail on anyone's project; a PR that hardcodes a domain will be rejected.
- **`crew/*.md` and `commands/*.md` must read as general heuristics, not a diary of this repo's bugs.** They ship into other people's repositories via the `shipmates` CLI, so a persona or workflow that only makes sense here is dead weight everywhere else it lands. If a defect found on Shipmates' own site (or anywhere else in this repo) prompts a fix to one of these files, extract the project-agnostic principle it teaches and write that — never the incident: no reference to this project, its selectors, its file paths, or its issue numbers.
- **Layout.** `commands/*.md` and `crew/*.md` are the **canonical sources** — harness-neutral, and the only files you edit for crew/command content. Per-harness payloads are compiled by the Rust CLI (`cargo run -- build --target <target>`): each adapter in `src/adapters/` emits the harness's frontmatter shape, and the shared render layer (`src/adapters/render.rs`) rewrites the neutral prose into the harness's real dialect — where its agents live (`.claude/agents/`, `.opencode/agents/`, …), what its session metadata is called, which project-instructions file it reads (`CLAUDE.md`, `AGENTS.md`), and how a role is spawned. Canonical `commands/*.md` frontmatter ships `name`, `description`, `argument-hint`, `allowed-tools`, `disable-model-invocation` — in that order. The Agent Skills standard requires only `name` and `description`, first, in that order; unknown keys are rejected, so a typo fails the gate rather than being silently ignored. **`name` MUST equal the parent directory name** — that is the standard's rule, and the skill will not resolve without it. `argument-hint`, `allowed-tools` and `disable-model-invocation` are **vendor extensions, not part of the Agent Skills standard** (`allowed-tools` does appear there, but as an experimental, space-separated key; ours stay comma-separated because that is what Claude Code parses). A harness whose skills ship as the strict Agent Skills pair (codex, antigravity, cursor, github-copilot, pi, windsurf) gets that pair plus the rendered body and nothing else — unknown keys would be rejected by a strict parser. Claude Code and grok-build accept the vendor keys natively and ship them rendered, so `disable-model-invocation` survives on both. `site/` is the GitHub Pages landing site (validated by `.github/scripts/validate_site.py`). `site/commands/<name>/index.html` are **generated** from the **rendered** Claude Code payload — the site documents what a user installs, and the neutral dialect (`{{issue}}`, `agent-files/*.md`) is not valid in any harness — by `tools/gen_command_pages.py` and committed; never hand-edit them; run `python3 tools/gen_command_pages.py` and commit the result. CI enforces this with `--check`. `site/docs/` are **hand-authored** reference pages (install, harnesses, troubleshooting, architecture) — the validator covers them, and `gen_command_pages.py` discovers them for the sitemap.
- **No shell script bodies in the workflow YAML — they live in `.github/scripts/`, and the step calls them.** A multi-line `run: |` block in `.github/workflows/*.yml` is a script hosted in the wrong place: it cannot be run or linted on its own, it buries the logic in a file a reviewer skims, and it silently loses `actionlint`'s shellcheck pass the moment it is extracted — so `.github/scripts/*.sh` carries its own gate (`bash .github/scripts/lint-shell.sh` in the Pages validate job) and must stay shellcheck-clean. Write a script as `bash .github/scripts/<name>.sh`; pass everything it needs from the GitHub context through the step's `env:` block (`TAG_FLAG: ${{ needs.plan.outputs.tag-flag }}`) and read it as a plain variable — never interpolate `${{ }}` into a script. Two values are exempt because they are **not ours**: cargo-dist's plan output supplies `matrix.install_dist.run` and `matrix.packages_install` as shell-specific command strings (sh on Unix, **pwsh on Windows**), so they stay inline with a comment — extracting them to a bash script would be unrunnable on the windows-msvc runner. A single-command `run:` (`cargo test --all-targets`) is an invocation, not a hosted script, and stays inline.
- **`$ARGUMENTS` is the only argument placeholder a `commands/*.md` may contain.** A skill has no positional arguments: indexed substitution is not in the Agent Skills standard, and its index base has changed between Claude Code versions, so a workflow written against one base silently reads the wrong argument on another. Parse `$ARGUMENTS` in prose instead ("the first word of `$ARGUMENTS` is the issue number"). **No `$` followed by a digit anywhere in the file — frontmatter and fenced code blocks included.** Substitution is textual over the whole file, so a fence protects nothing: run `/shipmates-ship-issue 42 focus on retries` and a shell snippet inside a fence that asks for field two is rewritten to ask for the literal word `on`. *(An earlier version of this bullet said fenced blocks were exempt because `$` + digit there is a shell field reference. That was wrong — nothing in the Claude Code docs describes a fence exemption, and the documented way to keep a literal is a backslash escape, which would be pointless if fences were exempt.)* If you genuinely need a literal, escape it — `\$2` — but prefer restructuring so you never do: `cut -f2` rather than an `awk` field reference. `cargo run -- check` enforces this over the whole file, fenced or not.
- **Catalogue commands ship interactive argument intake by default.** Declare a `## Parameters` table (Name / Required / Token / Values / Default / Help) immediately above Runtime input — every captain-facing knob is its own row with a Default, never a catch-all; shared picker rules live in [`docs/COST.md`](docs/COST.md)'s command-preamble (always show every row; enums show default plus other choices; then OK or type what to change) — do not copy them into each command.
- **Name by register — never bulk-substitute one noun for another.** Three terms, three jobs. A **skill** is the artifact on disk — `.claude/skills/<name>/SKILL.md`, the [Agent Skills](https://agentskills.io) open-standard shape. A **command** is a whole workflow the captain issues to the crew — `/shipmates-ship-issue`, `/shipmates-fix-bug`; the eighteen are **the commands**. An **order** is what a single subagent is told to do *within* a command — one specialist's instruction, never the workflow and never the set of eighteen. Use *skill* in tech-leading copy — install paths, layout and reference sections, frontmatter docs, contributor instructions, anything about the file on disk or cross-harness portability. Use *command* in brand-leading copy — the intro, the crew-and-commands framing, taglines, section headings that sell the metaphor, example usage. Two retired spellings: don't prefix "command" with "slash-" (Anthropic's pre-skills label, and Claude-Code-only — plain "command" is the product noun we want), and write **subagent** as one word, never hyphenated or spaced, matching the Claude Code, Cursor and OpenCode docs. "The crew" and "shipmates" stay as brand terms. Full statement, with the do/don't examples: [`docs/BRAND.md`](docs/BRAND.md#naming-register).
- **Every command is user-invoked only.** All eighteen set `disable-model-invocation: true`. You start one by typing `/shipmates-ship-issue`; Claude never loads one on its own. These workflows create worktrees, push branches and open pull requests, so the decision to start one stays with the captain. Per the Claude Code docs this does **not** affect direct `/name` invocation (`user-invocable` is the field that would), and it additionally keeps the skill out of subagent preloading and off scheduled-task triggering.
  **The same decision is why the eighteen land in `.opencode/commands/`, not `.opencode/skills/`.** opencode has both directories and they mean different things: its *skills* are model-invoked — the model loads one on demand through a native `skill` tool — and `disable-model-invocation` is not one of the frontmatter keys a `SKILL.md` recognises there, so writing it would be silently dropped rather than rejected. `commands/` is `/`-invoked only, which preserves user-invoked-only structurally instead of by a key the target ignores. This makes the naming register load-bearing rather than stylistic: on opencode, *commands* and *skills* are two real directories, so using the words interchangeably is actively wrong.
- **Captain starts gated commands.** A human `/`-invokes to begin. Mid-run: do not invent a second captain slash, flip the gate, or add Skill-tool exceptions.
- **Compose by Read + execute.** When a running gated command must reuse another's pipeline: Read that command's **installed, harness-rendered** file for the active target, then execute its stages in this session as source of truth. Do not invent a parallel stage list from memory. Call Skill / `skill` only if the name is in the harness listing; if it is absent, Read + execute.

- **Adding a frontmatter key to a canonical command?** You must add a harness entry per target in `tools/capability_registry.json` where the key maps a tool, and the reference digests must be regenerated: run `cargo run -- build --target <target> --update` for every implemented target and commit `tests/payload-digests/*.sha256` — never edit them by hand. They are regression fixtures: CI proves each freshly built payload matches its committed digest with `cargo run -- check --target <target>`, so a changed rendering rule fails loudly instead of shipping silently. Nothing under `tests/payload-digests/` is ever installed; what a user receives is compiled from `commands/` + `crew/` at install time.
- **Adding a harness?** Implement `src/adapters/<harness>.rs`, register it in `src/adapters/mod.rs` (module + `targets()`), wire it into the `select()` in `src/main.rs`, add the target to `targets` and `target_status` in `tools/manifest.json`, and map its tool names in `tools/capability_registry.json`. Adapters translate the semantic capabilities (`read`, `edit`, `bash`, `web`, `agent`) and the role `*-scopes` refinements — they must never put a target's tool names into canonical content. **Least privilege is the adapter's job, not the target's default.** Claude Code's permission model is an allowlist, so naming the tools a role needs is sufficient. opencode's is not: its shipped defaults are effectively `"*": "allow"`, so an allow-list alone grants nothing, and every generated opencode agent emits a `"*": deny` catch-all *first* and its specific allows after — that target resolves permissions last-match-wins, so the ordering is the mechanism. Codex is the exception to the Markdown assumption: its agents are standalone TOML at `.codex/agents/<name>.toml`, and it documents no per-agent tool allowlist, so least privilege genuinely cannot be expressed there — that gap is recorded in the adapter rather than faked with an invented key. A harness with no subagent mechanic ships the crew as skills only (`emit_skill_files` in `src/adapters/render.rs`), emitting the Agent Skills standard's `name`/`description` pair and nothing else; a new adapter must establish the equivalent for its own target and say so.
- **Never hard-code a specific model — the main agent picks from what is available at that moment.** Model names are the least stable thing in this ecosystem: vendors retire, rename and re-tier them on their own schedule, and what a given user can run depends on their plan, their sign-in and the harness in front of them. A concrete model ID written into content is brittle the day it lands and wrong within a release cycle. Name the **tier and the role** — `mechanical` / `judgment`, "cheapest capable", "top available" — and let the **main agent resolve that to a real model at spawn**, from the pool available to that user on that harness (#434); where the pool is unknown, **inherit**. This applies to every surface, not only canonical frontmatter: command and crew prose, adapter code and comments, `tools/harness_matrix.json` notes, docs, PR bodies and issue text. Where a document must illustrate a naming *scheme* — an alias set, a `provider/model` path, an effort suffix folded into a model string — write the **shape**, never a product name; a real ID in an example reads as a recommendation and rots.
- **An installed command is a snapshot; the user's harness is not. Degrade, never break.** A captain installs Shipmates once and then upgrades their harness whenever it ships, so version skew between the installed payload and the harness in front of it is the **normal** case, not an exception. Four ways a harness moves underneath a command: a **new model** is released, a **frontmatter key** is added, renamed or starts being rejected, a **discovery path** moves (the codex skill-path bug), or a **CLI flag, subcommand or tool name** changes. `tools/harness_watch.py` and the `verified_on` dates catch drift *after* we look — they cannot protect a captain whose harness is newer than the payload they installed. The safety net therefore belongs **in the command**: every harness-dependent step **names its fallback** (inherit the session model; fall back to `{{general-purpose}}` with the role brief inlined; gate a seat out and say so), and **verifies the surface exists before relying on it** rather than assuming the version it was written against. A command that hard-fails mid-workflow on an unknown key, a moved path or a retired model has moved the cost of our assumption onto the captain. Never let a step's success depend on a surface the user's harness has not been seen to confirm.
- **Per-agent model / reasoning-effort are harness features — emit only what the target's format actually has.** A **model is never stamped into canonical frontmatter**: harnesses offer different model sets (a per-agent `model:` value is meaningless on a target that resolves models at session level, and no single value is valid across every target) and users have different access, so which model a role runs on is a **runtime** decision the orchestrator makes at spawn (inheriting where a harness has no per-spawn override), not an install-time value — the adapters emit no model (#205). **Reasoning effort** (`low`..`max`) *is* a static per-role feature the adapter stamps into frontmatter, but **only on the harnesses whose agent format carries the key**: Claude Code (`effort`), Codex (`model_reasoning_effort`), Cursor (folded into the model string), opencode (`reasoningEffort`, a provider passthrough). Antigravity, GitHub Copilot, Pi, and Windsurf/Devin get **no effort key from the adapter** — record that *emission* gap in the adapter (as codex does for its missing tool allowlist) rather than inventing a key (#204). What each target's model surface *documents* is a separate axis: whether the orchestrator can route a model or an effort at spawn is recorded per harness in `tools/harness_matrix.json` under `model_surface`, never confused with what we emit. As with tool names and install paths, this is per-harness *static feature support*: verify it against the harness's first-party docs (`tools/harness_watch.json`) before an adapter emits it. **How the spawn resolves that model** — the query → documented-surface → `inherit` discovery ladder, the resolution order, and the enforcement and audit rules — is canonical in [`docs/COST.md`](docs/COST.md) (`## Model routing`); the per-harness model surface is recorded in `tools/harness_matrix.json` under `model_surface`, and the decision itself is [`docs/adr/0003-the-orchestrator-judges-the-model.md`](docs/adr/0003-the-orchestrator-judges-the-model.md), which supersedes the declared-config half of [`docs/adr/0002-available-model-pool-discovery.md`](docs/adr/0002-available-model-pool-discovery.md).

### Principles for developing Shipmates the right way

These are load-bearing lessons, not style preferences. Break one and something silently ships broken.

- **Know which of three scopes a file belongs to before you change it, test it, or assert anything about it.** They look alike and are not. **Canonical resources** — `commands/`, `crew/`, `toolbox/`, `steering/`, `docs/COST.md` — are embedded by `build.rs` and installed into a **consumer's** repo. **The product** — `src/` — is the CLI itself. **This repo's dev environment** — `CLAUDE.md`, `.github/`, editor and tooling config — is never embedded, never installed, and invisible to every consumer. A fact about one scope is not a fact about another, and a field that describes a **target** (a `Dialect` value, a `harness_matrix.json` entry) describes the *consumer's* repo, never ours, so it can never become a guard for our own files. Tests follow the same line: `cargo test` covers the product, so a repo-hygiene invariant belongs in a repo-level check under `.github/scripts/` or `tools/` — never in the product's test suite, where it would also fail for anyone running the tests against a packaged crate. Learned the hard way: a `CLAUDE.md` regression test walked the render dialects to assert a root instruction file existed in *this* repo, conflating the filename our commands tell an agent to look for in *someone else's* project with the file ours happens to have. The test was removed — it proved nothing about the payload and belonged to no scope it was testing.
- **Research defaults to each harness's first-party docs — every supported target, every time.** Any question about what a harness can do — a capability, a frontmatter key, a discovery path, a spawn-time override, a model surface, a CLI flag — is answered from **that harness's own documentation**, checked harness by harness. Cover **every target in `tools/harness_matrix.json`**, not the two or three that were quick to check: read the list from the registry rather than from a sentence like this one (currently claude-code, opencode, antigravity, codex, cursor, github-copilot, pi, windsurf, grok-build). Start from the per-harness first-party doc URLs already recorded in `tools/harness_watch.json`. Never generalize one target's behaviour to another, and never answer from memory or a third-party summary where a first-party doc exists. The expected shape of a research answer is a per-harness table with a row for **all** of them; a harness that lacks the feature is a **finding, stated out loud** ("antigravity has no per-agent effort field"), never a silent blank. Cite the doc URL and the date checked, and deposit the verdict in `tools/harness_matrix.json` / `tools/harness_watch.json` so the next agent inherits the finding instead of re-deriving it. A confident answer that happens to be right for Claude Code and wrong for Codex is the exact failure this rule prevents.
- **Ground every harness change in that harness's first-party docs before writing the adapter.** Where it discovers skills and agents, and which frontmatter keys it accepts, are facts to verify against the harness's own documentation — never assumptions. This is how the codex skill-path bug was caught: it reads the open Agent Skills location `.agents/skills/`, not a private `.codex/` tree, so installing to the private tree meant the harness never loaded anything. `tools/harness_watch.py` (config in `tools/harness_watch.json`, run it or `/harness-watch`) fetches each harness's docs and flags when they drift from what an adapter assumes; CI runs its offline config-consistency check.
- **One source of truth; compose, never duplicate.** Four harnesses (codex, antigravity, github-copilot, pi) read the shared open `.agents/skills/` tree, so their skills — and tools — render **once**, in the neutral `AGENT_SKILLS` dialect (`render.rs`), via `emit_shared_skills`/`emit_shared_tool_skills`, and every one gets byte-identical files. Rendering per-harness into a shared path means a multi-harness install collides (last writer wins). Keep every specific adapter and share through composition; cursor renders the same neutral dialect but writes it to its first-party `.cursor/skills` — the only tree its slash-command picker reads (#405) — and writes it there *only*, because a second copy in the shared tree would list every command twice and pay for the payload twice; a **global** Pi install omits command skills (#513) because Pi also loads `~/.pi/agent/skills` in the same session as project `.agents/skills`; windsurf stays on its canonical `.windsurf/skills`, claude-code on `.claude/skills`, opencode on `commands/`, and grok-build on its own `.grok/skills` — its commands ship the native `disable-model-invocation` guard, which the neutral shared dialect does not carry.
- **Tools are the third resource type** (after crew and commands): the model-invoked sibling of a command — the crew reach for one implicitly, never by typing a slash. Defined once in `toolbox/<name>/`, which holds **exactly `tool.md` + one runnable `<name>.py` and nothing else** — `build.rs` embeds the directory and the installer copies every file into users' skill dirs, so a stray `__pycache__` or spec ships as garbage. Mapped at install by `Adapter::build_tools`: a native code tool on opencode (`.opencode/tools/<name>.ts`), an agent-invoked Agent Skill in the shared `.agents/skills/` tree elsewhere — `.cursor/skills/` on cursor, which reads only its first-party tree (#405), and `.grok/skills/` on grok-build, whose whole skill tree is native because its commands carry the guard — (agent-only on Claude Code via `user-invocable: false`). Tool pages are **generated** from `TOOLS`/`TOOL_COPY` in `tools/gen_command_pages.py` — never hand-edit `site/tools/<name>/`; example assets live under `site/tools/<name>/examples/`.
- **Tools ship by default on install; stay decoupled from commands.** A plain `install` includes the full toolbox; `--with-tools none` is the escape hatch for minimal crew-only installs (e.g. `/shipmates-ship-issue` worktrees). Never couple a command or crew member to a tool.
- **A tool must work out of the box — the user never installs a dependency by hand.** Prefer stdlib-only. If a tool genuinely needs a package (e.g. Pillow for image output), it self-provisions into a private virtualenv on demand rather than printing "run `pip install …`". "Self-contained" means it runs after `shipmates install`, full stop.
- **The generator owns generated pages; extend the model, then regenerate.** `tools/gen_command_pages.py` produces every `site/commands/<name>/`, `site/agents/<name>/`, `site/tools/<name>/` page **and** the sitemap from `SLUGS`/`AGENT_COPY`/`TOOL_COPY`. Add to those and run `python3 tools/gen_command_pages.py`; `--check` gates drift in CI. Hand-editing a generated page is reverted on the next run and fails `--check`.
- **Verify behaviour end to end; don't trust that it works.** Before pushing a tool or install change: re-run the renderer independently and *look at the output*; install via the real CLI from the **embedded** payload (an empty directory, no checkout — the brew/cargo path) and invoke each tool from its installed location. Run the full local gate set (cargo build/test, `check --target` digests for all targets, `gen_command_pages.py --check`, `validate_site.py`, `validate_design_drift.py`, unittest, `test_resolve_src.sh`, `harness_watch.py --offline`) and poll CI green after every push. **A check is not evidence until you have watched it fail.** When verifying that something is *loaded, discovered or inherited* rather than computed, close the escape hatch first: a subject that can go find the answer itself will, so a positive result without a negative control measures the wrong mechanism. (A tool-enabled Claude Code session read `AGENTS.md` off disk and answered correctly in *both* arms of a test about instruction loading, which would have "proved" the opposite of the truth; with tools denied, the arm lacking a pointer correctly reported no instructions in context.) Delegating a build to a subagent does not remove the obligation to independently verify its output.
- **Never commit a vendor-key-shaped string, even a fabricated one.** `sk_live_…` (Stripe), `ghp_…` (GitHub) and friends trip GitHub push protection and block the push regardless of intent — the scrub example log learned this the hard way. Use prefix-less, credential-shaped fakes in examples; detectors that match by shape still redact them.
- **Write user-facing copy with confidence — never undersell or disclaim the product's own work.** No "nothing to do with shipmates", no apologetic or hedging framing on a page describing a shipmates feature. Say what the thing is and does, plainly and positively. (Full voice guidance: [`docs/BRAND.md`](docs/BRAND.md#voice-and-tone).)
- **The two meta commands are `/shipmates-report-bug` and `/shipmates-upgrade`.** Unlike domain-neutral crew roles and the other sixteen workflow commands, they may name Shipmates, harnesses, and the upstream repo `saman-mb/shipmates` explicitly — `/shipmates-report-bug` files structured bug reports upstream, and `/shipmates-upgrade` checks for a newer Shipmates release and refreshes, audits, and repairs the installed crew from a captain's project. Domain neutrality applies everywhere else.
- **Prompt cost discipline.** [`docs/COST.md`](docs/COST.md) is source of truth for the six cost principles and shared preambles. Keep stable command/subagent instructions before volatile input, and require compact decision-shaped returns instead of transcripts.
- **Release-affecting `/shipmates-ship-issue` PRs include the version bump.** When a story changes what the published binary or install payload ships (commands, tools, crew, `Cargo.toml`), bump the version and add a `CHANGELOG.md` entry **in the same PR**. Merge to `main` without a new version is a no-op for the release workflow (`.github/workflows/release.yml` publishes only when the version tag is new).
- See [`CONTRIBUTING.md`](CONTRIBUTING.md) for the full contribution guide.

## Scope & honesty

- **Claude Code is fully runtime-verified; four more have captain-attested live runs; four are format-only.** opencode, Antigravity CLI, Codex CLI, Cursor, GitHub Copilot, Pi, Grok Build and Windsurf each have an adapter — `shipmates install --harness <name>` produces their trees, every payload's format was checked against the harness's own parsing source and first-party docs, and each target's digest is gate-checked in CI. opencode, Antigravity, Codex CLI, GitHub Copilot, Pi and Grok Build receive the full crew + all 18 commands; Cursor and Windsurf ship the 18 skills only. Grok Build installs into its own native tree — crew at `.grok/agents/<name>.md`, the commands and the toolbox at `.grok/skills/<name>/SKILL.md`, project steering at `.grok/rules/shipmates-contributor.md` and global steering at `~/.grok/AGENTS.md` — and not the shared `.agents/skills/` tree, because its commands ship the native `disable-model-invocation` guard that the neutral dialect carries no room for. It is the one non-Claude target that keeps that guard, and it enforces a per-agent tool allowlist and carries static per-role effort. One gap is recorded rather than papered over: Grok Build cannot hide a skill from its slash menu without hiding it from the model, so a toolbox tool is agent-invoked yet still typeable. Pi's crew are resolved by the third-party `pi-subagents` extension, not by core pi — an install without that extension resolves no crew, and that dependency plus pi's project-root scope limit are recorded in `tools/harness_matrix.json`. Static capability evidence lives under `agents_notes` (and related fields); **live runtime evidence** lives under each harness's `runtime_verified` record in the same file — `status` (`full` / `partial` / `none`), `verified_on`, and the distinct claims `crew_resolve`, `argument_passing`, `command_e2e`, plus `commands_exercised`.
