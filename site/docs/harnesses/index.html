🌊 Harnesses

Harness matrix

Which harnesses the crew runs on, and what's coming next.

The installer knows eight harness roots, but known is not shipped: a payload is built for a harness only when we've verified it can keep every safety property the commands rely on. Two clear that bar today — and only one of them has been run for real.

The matrix

Shipped means the payload is exported from neutral canonical sources, byte-compared against the committed golden reference and the generated agents/ + skills/ mirrors, compiled at install time, and the harness is one Shipmates has actually been run on. Only claude-code meets all of that.

Builds, not runtime-verified is opencode, and it is a deliberately narrower claim. install.sh --harness opencode produces the full crew and all twelve commands, and the payload format was verified against opencode's own parsing source and its first-party docs. It has not been exercised against a running opencode — whether agents resolve, whether argument passing behaves, and whether /ship-issue completes end to end are open questions tracked in #31 and #32. Nothing on this site should be read as “tested on opencode”.

In development means the harness has a tracking epic and we're actively building its adapter. Planned means we intend to support it but haven't started. Six targets still have no adapter and the exporter refuses them.

Why not yet?

Every one of the twelve commands ships disable-model-invocation: true — you start one by typing /ship-issue; the model never loads one on its own. These workflows create worktrees, push branches, and open pull requests, so the decision to start one stays with the captain.

Before we build a payload for a new harness, we verify it has an equivalent guard. The six harnesses without an adapter don't document one yet, so the capability matrix holds their payloads back. The moment a harness documents an equivalent, the matrix entry flips and a payload appears.

The three harnesses with tracking epics are in active development — their adapter stories include verifying this exact property. The mechanics of how the matrix works are on the architecture page.

How opencode cleared the guard

opencode has no disable-model-invocation equivalent either. It cleared the guard a different way — by using a directory where the property holds structurally.

The twelve install as commands, not skills. opencode has both, and they are different things. Its skills are model-invoked: the model loads one on demand through a native skill tool, and disable-model-invocation is not among the frontmatter keys a SKILL.md recognises there — declaring it would be silently dropped rather than rejected. So the twelve go to .opencode/commands/<name>.md, which is /-invoked only. The captain still decides when a run starts, and that now rests on the directory rather than on a key the target ignores.

Least privilege survived, by inversion. Claude Code's permission model is an allowlist, so naming the tools a role needs is enough. opencode's defaults are permissive — effectively "*": "allow" — so an allow list alone would restrict nothing. Every generated opencode agent instead writes a "*": deny catch-all first and its specific allows after; opencode resolves permissions last-match-wins, so that ordering is what makes it hold. The result is marginally stronger than the Claude posture: a tool a wildcard denies is hidden from the model entirely rather than refused when it is called.

Role-level refinements survive the translation too. art-director declares web-scopes: search once in the canonical sources, and gets WebSearch without WebFetch on Claude Code, and websearch: allow without webfetch on opencode.

opencode is also the only non-Claude harness that receives subagents — .opencode/agents/<name>.md, each with mode: subagent — because it is the only one with a documented native subagent directory.
