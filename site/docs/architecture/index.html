🧭 Architecture

Architecture

How the matrix, generator, and installer fit together.

One canonical source tree, one declarative matrix, one generator, one installer. The rule that keeps them honest: generated trees are committed, and CI fails on drift.

On this page

  • The two trees
  • Frontmatter contract
  • The capability matrix

The two trees

The canonical source is Claude Code's shape. Everything else is derived.

agents/                      skills/
  architect.md                 ship-issue/
  senior-engineer.md             SKILL.md
  sdet.md                        fix-bug/
  … (12 personas)                  SKILL.md
                               … (12 commands)

agents/*.md are the subagent personas — frontmatter (name / description / tools) plus a system-prompt body. skills/<name>/SKILL.md are the command workflows, in the Agent Skills open-standard shape. The installer drops both trees into a harness root: agents/ lands at <root>/agents/, and each skills/<name>/ directory lands at <root>/skills/<name>/ — copied whole, so whatever a skill bundles (references/, scripts/, assets/) travels with its SKILL.md.

The same split holds on the published site: site/commands/<name>/index.html pages are generated from the skills, while these docs pages are hand-authored.

Frontmatter contract

What a SKILL.md may declare, and in what order.

KeyStatusNotes
namerequired, firstMust equal the parent directory name — the standard's rule, and the skill will not resolve without it.
descriptionrequired, secondWhat the workflow does; the only other required key.
argument-hintvendor extensionClaude Code extension, not part of the Agent Skills standard — the usage hint shown when you type the command.
allowed-toolsvendor extensionComma-separated in the canonical sources because that is what Claude Code parses; the standard's experimental form is space-separated.
disable-model-invocationvendor extensiontrue on all twelve — every command is user-invoked only; the model never loads one on its own.

The standard's optional license, compatibility, and metadata keys may appear after the two required ones, in any order. Unknown keys are rejected, so a typo fails the gate rather than being silently ignored. In the body, $ARGUMENTS is the only argument placeholder a skill may contain — positional substitution is not in the standard, and tools/validate_skills.py enforces it.

The capability matrix

tools/harness_matrix.json — the single source of truth for what may leave the repo.

The matrix is declarative: feature × harness → policy. A top-level harnesses block records whether a target gets an agents/ tree at all (today: claude-code and opencode — though opencode's payload is refused for a different reason, see below). Under features, each frontmatter key (name, description, license, allowed-tools, disable-model-invocation, tools, model, …) carries an applies_to list (skills / agents) and, per harness, either supported: true — optionally with a separator for list values — or a policy: drop, warn, emulate, or refuse.

The matrix itself is validated at load: version, known policies, every feature covering every harness exactly, an emulation note present if and only if the policy is emulate. And the contract cuts both ways — a frontmatter key the matrix does not cover is a hard error, not a silent passthrough. Adding a key to a canonical skill means adding a matrix entry per harness, or the build fails.

Payload generation

tools/build_harness_payloads.py projects the canonical trees into harnesses/<target>/.

For each (feature, target) pair, the matrix entry decides what the generator emits:

  • supported — emit the key, respelled if the matrix names a different spelling, and with comma-separated values rewritten to the standard's space-separated form when the entry declares separator: "space".
  • drop — omit the key silently; cosmetic loss only (argument-hint is dropped everywhere but claude-code).
  • warn — omit the key and print one machine-readable JSON line on stderr recording exactly what was lost.
  • emulate — omit the key and append a deterministic “Harness adaptation” section to the body expressing it in prose.
  • refuse — fail the whole target before anything is written. Reserved for safety properties: every shipped command sets disable-model-invocation: true, and a harness with no equivalent gets no payload rather than an auto-invocable command.

Output is deterministic and committed, matching the repo's other generators — regenerate with python3 tools/build_harness_payloads.py, never hand-edit. The claude-code tree is a byte-for-byte mirror of the canonical sources; today it is the only tree under harnesses/, because every other target refuses on disable-model-invocation — see the harness matrix.

Install flow

install.sh --harness consumes the generated tree, never the canonical one.

With --harness <name>, the payload comes from harnesses/<name>/ — the matrix-generated, transformed tree — not from skills/ + agents/. A missing tree means the matrix refused to build it, and the installer refuses too: Shipmates: no payload for '<name>' — the capability matrix refused to build one. The gate runs before any directory is created, so a refused harness fails without touching the filesystem.

No --harness is one implicit claude-code run, byte-identical to a pre-harness install (claude-code is the exception that reads the canonical tree, since its generated tree is identical anyway). --harness all expands to every known harness; the flag is repeatable and dedupes; unknown names are a hard error listing the known ones. Every harness root gets its own manifest, so --uninstall works per harness. Subagents ship for claude-code only — no other harness documents a compatible subagent directory for the frontmatter format Shipmates ships, so those targets get a skip note instead of files they may mishandle.

CI gates

The Validate site job in pages.yml gates every PR; deploy runs only on pushes to main.

The job gates the sources (skills/) and the site built from them, in that order — a bad SKILL.md is reported against the file someone edited, not against a derived page:

  1. python3 tools/validate_skills.py — the frontmatter contract and the $ARGUMENTS rule.
  2. python3 tools/validate_skill_names.py --check — skill names must not collide with harness built-ins.
  3. python3 tools/gen_command_pages.py --check — the generated command pages (and sitemap) are up to date.
  4. python3 tools/build_harness_payloads.py --check — the committed harnesses/ trees match what the matrix would generate.
  5. python3 .github/scripts/validate_site.py — the static site: one <h1> per page, heading outlines, self-containment, local refs, SEO metadata, JSON-LD, page and docs coverage, and the sitemap.
  6. An executable-bit check on install.sh, so the piped-to-Bash entry point never loses its mode.

The --check steps are drift detectors: they regenerate in memory and fail on any difference, so a hand-edited generated file — a command page or a harness payload — cannot merge.
