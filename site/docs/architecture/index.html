🧭 Architecture

Architecture

How the canonical sources, adapters, and installer fit together.

Neutral canonical sources, one Rust CLI, per-harness adapters. The rule that keeps them honest: every target's output is byte-compared against a committed digest, and CI fails on drift.

The canonical sources

Neutral, harness-agnostic, and the only files you edit for crew or command content.

commands/                  crew/
  ship-issue.md               architect.md
  fix-bug.md                  senior-engineer.md
  plan-epics.md               sdet.md
  … (12 commands)             … (12 personas)

commands/*.md are the twelve workflows, in the Agent Skills open-standard shape. crew/*.md are the twelve subagent personas. Both are written in a neutral dialect — $ARGUMENTS is the only argument placeholder a command may contain, and no file may name-drop a stack, framework, or product. Every harness's payload is rendered from these two trees; nothing domain-specific belongs here.

The published site mirrors the split: site/commands/<name>/index.html pages are generated from the rendered Claude Code payload, while these docs pages are hand-authored.

Frontmatter contract

What a SKILL.md may declare, and in what order.

KeyStatusNotes
namerequired, firstMust equal the parent directory name — the standard's rule, and the skill will not resolve without it.
descriptionrequired, secondWhat the workflow does; the only other required key.
argument-hintvendor extensionClaude Code extension, not part of the Agent Skills standard — the usage hint shown when you type the command.
allowed-toolsvendor extensionComma-separated in the canonical sources because that is what Claude Code parses; the standard's experimental form is space-separated.
disable-model-invocationvendor extensiontrue on all twelve — every command is user-invoked only; the model never loads one on its own.

The standard's optional license, compatibility, and metadata keys may appear after the two required ones, in any order. Unknown keys are rejected, so a typo fails the gate rather than being silently ignored. In the body, $ARGUMENTS is the only argument placeholder a command may contain — positional substitution is not in the standard, and tools/validate_skills.py enforces it over the whole file, fenced code blocks included.

Adapters & dialects

One adapter per harness in src/adapters/, sharing one render layer.

Each harness is a Rust adapter (src/adapters/<harness>.rs) that declares a Dialect: where its agents live (.claude/agents/, .opencode/agents/, .agents/agents/, …), what its session metadata is called, which project-instructions file it reads (CLAUDE.md, AGENTS.md), and how a role is spawned. The shared render layer (src/adapters/render.rs) rewrites the neutral prose into the harness's real dialect.

Tools are resolved from semantic capabilities, never hardcoded per harness: read → Read/Grep/Glob, edit → Write/Edit, bash → Bash, web → WebSearch/WebFetch, agent → Agent. A role's *-scopes refinements are preserved in each harness's own permission model.

Least privilege is the adapter's job, not the target's default. Claude Code's permission model is an allowlist, so naming the tools a role needs is sufficient. opencode's shipped defaults are effectively "*": "allow", so an allow-list alone grants nothing — every generated opencode agent emits a "*": deny catch-all first and its specific allows after, and opencode resolves permissions last-match-wins, so the ordering is the mechanism.

A harness with no subagent mechanic — cursor, windsurf and zed — ships the crew as skills only (emit_skill_files): the twelve commands as skills/<name>/SKILL.md, with the Agent Skills standard's name/description pair and nothing else — vendor keys like allowed-tools or disable-model-invocation would be rejected by a strict parser. That covers codex, cursor, github-copilot, windsurf, and zed; the crew drops out entirely.

The registries

tools/manifest.json and tools/capability_registry.json — what the CLI knows about its targets.

tools/manifest.json declares the canonical source roots (commands/, crew/), the project-instructions mapping, and every target with its build status — eight names today (claude-code, opencode, antigravity, codex, cursor, github-copilot, windsurf, zed), all marked implemented. tools/capability_registry.json maps the semantic capabilities and role *-scopes to each harness's tool names — the thing adapters consult, and the only place a harness's tool names live (never in canonical content).

The contract cuts both ways: adding a frontmatter key to a canonical command means registering it in the capability registry and regenerating every target's reference digest, or the build fails.

Payload generation

shipmates build --target <name> renders the canonical trees into harnesses/<target>/.

For a chosen target the adapter renders every command and persona into that harness's dialect, returning the complete file map. shipmates build --target <name> writes it under harnesses/<target>/; --out redirects. Output is deterministic and byte-compared against a committed reference: shipmates check --target <name> verifies the fresh build matches tests/payload-digests/<name>.sha256, and shipmates update --target <name> (or build --update) regenerates the digest. Never hand-edit a digest — they are regression fixtures; CI proves each freshly built payload matches.

Two dialect choices are load-bearing. The name of a skill must equal its parent directory name, and the twelve commands ship disable-model-invocation: true — every command is user-invoked only. On opencode, which has no such frontmatter key, the twelve land in .opencode/commands/ where user-invocation holds structurally; the full reasoning is on the harness matrix.

Install flow

shipmates install --harness <name> [--dir <path>] drops the harness's own tree at the target root.

The CLI reads the canonical sources from the current directory (or --root for the build/check/update commands), runs the selected adapter, and writes the payload — stripping the harnesses/<target>/ container so the harness's own tree (.claude/, .opencode/, .codex/, …) lands where the harness actually reads it. Default target directory is the current one; --dir pins an explicit root. --harness all expands to every harness, and shipmates targets lists them.

Subagents ship to claude-code, opencode, and antigravity — the harnesses with a documented native subagent directory. The five skill-only harnesses get the twelve skills and nothing else; there is nowhere for agents/*.md to go.

CI gates

The Validate site job in pages.yml gates every PR; deploy runs only on pushes to main.

The validate job gates the sources (commands/ + crew/) and the site built from them, in that order — a bad SKILL.md is reported against the file someone edited, not against a derived page:

  1. python3 tools/validate_skills.py — the frontmatter contract and the $ARGUMENTS rule.
  2. python3 tools/validate_skill_names.py --check — skill names must not collide with harness built-ins.
  3. python3 tools/gen_command_pages.py --check — the generated command pages (and sitemap) are up to date.
  4. cargo run -- check --target <name> for every one of the eight targets — each fresh payload matches its committed tests/payload-digests/<name>.sha256.
  5. bash tests/test_validate_skills.sh — the skill-lint regression suite.
  6. python3 tools/gen_demo_gif.py --check — the demo GIF/poster artifacts are up to date (pinned Pillow + font, byte-compared as pixels).
  7. python3 .github/scripts/validate_site.py — the static site: one <h1> per page, heading outlines, self-containment, local refs, SEO metadata, JSON-LD, page and docs coverage, and the sitemap.
  8. python3 .github/scripts/validate_design_drift.py — design-system drift check.
  9. python3 -m unittest discover -s tests and bash tests/test_resolve_src.sh — the Python test suite and the install source-resolution regression.

A second job, exporter-floor, builds and checks every target on a minimum environment, then runs three real installs end to end (claude-code, opencode, and a skill-only harness) asserting the right files land in the right trees. The --check steps are drift detectors: they regenerate in memory and fail on any difference, so a hand-edited generated file — a command page, a site asset, or a digest — cannot merge.
